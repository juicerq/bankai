# OpenCode is read from its own database through a mirror file

OpenCode joins Claude and Codex as a third Harness. Its CLI keeps everything in one SQLite database — `$XDG_DATA_HOME/opencode/opencode.db` (defaulting to `~/.local/share`), tables `session`, `message`, `part` — so the harness reads that database directly with the runtime's own `node:sqlite`, opened read-only, and never spawns the `opencode` binary the way the Codex harness once spawned an app-server.

Discovery walks `/proc` for processes whose comm is `opencode` and keeps only interactive TUI invocations; a resumed session id is taken from the command line's `--session`/`-s`, otherwise the process binds to the most recently updated root session in its working directory. Status comes from evidence in the database: an assistant message without a completion time is an open turn, so Working; a running `question` tool part on top of it means the agent is blocked on the user, so Needs attention; anything else is idle. Permission requests are delivered only as transient server events and are never written, so they stay invisible — the same blind spot Codex has, accepted for the same reason ADR-0005 accepts registry-less CLIs.

The conversation engine tails files, and OpenCode writes rows, not lines. So the harness keeps a mirror: one JSONL file per subscribed session under Bankai's data directory, rebuilt whole when first seen after a launch and appended afterwards from a `time_updated` watermark, pumped by the activity tick that already runs every `ACTIVITY_POLL_MS`. Re-emitted parts carry their original part ids, so the existing merge-by-id replaces streamed text in place; the parser drops re-emissions whose content did not change. Subagent sessions hang off the `task` tool part's metadata, which names the child session id.
