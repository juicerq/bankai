# Service output belongs to the Service, not to a Project

The Services list names every Service across every mounted Project, but what the workspace area shows is decided by the Project of the Selected session, so a Service's output was reachable only when its Project happened to be the Selected session's Project: opening it made that Project resident, mounted and hidden, and never visible. A global list fed a pane that was not, and the binding was incidental rather than designed — the pane's terminal depends on no Project-scoped context, it was simply rendered inside one. The second half of the same problem was retention: each shell process keeps a 1 MB scrollback ring in the main process and the whole record, ring included, is deleted synchronously the moment the process exits, clean stop and crash alike, so a Service that died took its own error output with it and attaching afterwards failed outright — the one reading the user wants most was the one guaranteed to be gone. We decided the Service output is a top-level pane addressed by Service and independent of any Project, and that the main process retains a dead Service's last 1 MB in memory until that Service starts again or Bankai closes, never on disk. The costs are accepted deliberately: the workspace area shows either a Shell or a Service output and never both, so selecting a session closes the output; retained output holds memory for services that will not run again in this launch; and nothing survives a restart, so a crash discovered the next morning is still unreadable.

## Consequences

- Retention is keyed by the Service and cleared by that Service's next start, so a service that dies and restarts in a loop never accumulates. What a launch can hold is bounded by how many distinct Services have died in it, not by how often they died.
- Nothing else needed a Service's Project to be resident. Mounting it to reach the output was the inherited path, and with the pane addressed by Service that reason is gone.
